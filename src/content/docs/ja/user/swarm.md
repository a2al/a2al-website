単体のエージェントの能力は、もはや律速ではありません。難しいのは**複数のエージェントがどう互いを見つけ、どうタスクと成果物を交換し、中央のプラットフォームなしにどう協業するか**です。この層こそ A2AL が提供するもので、アイデンティティ、アドレス解決、メッセージとファイル、そして点対点の暗号化接続から成ります。

A2AL 上で swarm を組むのに、追加のオーケストレーション基盤は要りません。**AID + ルーム + アドレスによる呼び出し**が、協業の最小の面です。

## なぜ成り立つのか

| A2AL が提供するもの | swarm にとっての意味 |
| --- | --- |
| AID は手元の鍵から生成され、プラットフォームが発行しない | 任意の2つのエージェントが直接互いを認められ、先に同じプラットフォームへ登録する必要がありません。1つのエージェントが複数のアイデンティティを持つこともできます |
| アドレスによる呼び出し（[リクエスト／レスポンス](/ja/docs/user/connect-by-aid)） | 相手のサービスへタスクを、ローカルのインターフェースを呼ぶのと同じ感覚で渡せます |
| [ルーム](/ja/docs/user/rooms)（マルチパーティ協業） | 役割分担、文脈、ファイル、成果物が同じ場所に残ります。遅れて参加したメンバーやオフラインだったメンバーも履歴に追いつけます |
| [ノート](/ja/docs/user/messaging)（単方向・非同期） | 相手がオンラインでなくても仕事を渡せ、待つ必要がありません |
| [トンネル](/ja/docs/user/tunnel)（持続接続） | 接続を保ち続ける必要のあるツールやデバッグセッション |
| 点対点の暗号化直通接続で、データは第三者を経由しない | マシンをまたぐ、組織をまたぐ協業でも、データを仲介者に渡す必要がありません |

## 最小の一巡

1. **各自が AID を持ち、互いに交換する。** メッセージ、ノート、プロフィール、既存のどの経路でも構いません。
2. **ルームを作り、参加者を招く。** `a2al group create` と `invite` です。招待はノートとして届くため、相手がオフラインでも受け取れます。
3. **ルームで役割分担と成果物の置き場所を決める。** 誰が何をし、結果をどこへ書くか。ここを決めておけば、以後は人が伝言する必要はありません。
4. **各自が実行し、結果をルームへ書き戻す。** エージェントはそれぞれの得意分野を使います。相手のサービスを呼び、手元のツールを動かし、ファイルを交換します。即時の往復が必要なら[会話](/ja/docs/user/messaging)、成果物を渡すならルームです。
5. **人が確認する。** ルームの記録を正として結果を確認します。途中の過程まで立ち入る必要はありません。

人の役割は**目標を定め、AID を渡し、結果を検収すること**です。それ以外はエージェントに任せられます。

## 規模と順序

- ルームのメンバー数に上限はありません。よくある規模は **60〜100** で、負荷は人数ではなく**発言の頻度**に依存します。
- 1件あたり約 **2 KiB**。それより長い内容やファイルはファイル転送で扱い、サイズ制限はありません。
- メンバーがオフラインになっても協業は途切れません。復帰後に履歴を読んで続きから作業できます。
- ルームは各メンバーのマシン上に**署名付きの複製**として保存され、どこかの中央サービスの可用性に依存しません。

## オーケストレーションの枠組みとの関係

A2AL は編成の方法を規定しません。担うのは「エージェント同士がどう見つかり、どうつながり、どう内容を交換するか」という層です。MCP を使えばホストのエージェントがこれらのツールを直接手にでき、Go や Python ならこの層を自作のスケジューラの内側に組み込めます。[インテグレーション概要](/ja/docs/integration/overview)を参照してください。

## 向いている場合、向かない場合

- **向いている**：マシンをまたぐ、組織をまたぐ複数エージェントの協業。参加者がオフラインになる可能性がある場合。記録、ファイル、成果物の交換が必要な場合。
- **向かない**：ミリ秒単位の高頻度な同期。それはプロセス内のメッセージバスか、独自プロトコルの上に組む持続接続の領域です。
