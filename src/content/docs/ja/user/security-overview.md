A2AL のアイデンティティと接続は中央のサービスに依存しません。**アイデンティティは手元の鍵で決まり、接続は両端の間の点対点の暗号化直通接続**です。ネットワーク層が担うのはアドレス解決だけ——AID を現在のエンドポイントへ、能力名を AID へ解決するだけで——メッセージやファイルがそこを経由して転送されることはありません。以下、アイデンティティと鍵、接続、メッセージと記録、アクセス制御の順に述べ、最後に A2AL が何を提供し、何を約束しないのかをまとめます。

本ページは仕組みと境界を説明するものです。日々の運用に関する指針（ポート、ACL、隔離運用）は[セキュリティ実践](/ja/docs/user/security-practices)にあります。

## アイデンティティと鍵

| 項目 | 説明 |
| --- | --- |
| AID | 手元で生成した Ed25519 鍵から派生します。発行、取り消し、付け替えができるプラットフォームはありません。マシンやネットワークを変えても変わりません |
| マスターキー | 作成時に一度だけ表示され、以後はあなたが保管します。`a2ald` は保存しません |
| 日常の署名 | マスターキーはオフラインのまま、日常的な記録は操作用のユーザー鍵と委任証明（delegation）で署名します |
| 復元 | 新しいマシンでマスターキーからアイデンティティを復元すれば、AID は変わりません（パネルの「新しいアイデンティティを追加 → マスター秘密鍵から作成」、または `a2al agents import`） |

マスターキーはアイデンティティそのものです。**失えば取り戻せず、漏れればなりすまされます。** A2AL は鍵を預からず、AID の復元や取り消しを代行することもできません。

## 接続：点対点の暗号化直通接続

1. AID を現在のアドレス記録へ解決し、候補エンドポイントを得る。
2. 候補エンドポイントへ同時に接続を試みる（IPv6 を優先）。
3. 双方が自分の Ed25519 鍵から導いた証明書で**相互 TLS** を完了する。身元の検証はハンドシェイクの内側で完結し、CA、ドメイン名、証明書配布に依存しません。
4. 直通がいずれも失敗し、アドレス記録にシグナリング用アドレスがある場合は、WebSocket 上の ICE に切り替えます。

NAT 越えは `a2ald` が自動的に行います（相手側反射、UPnP、ICE による穴あけ）。**A2AL は中継を設けません。** データは両端の間を暗号化されて流れます。双方が対称 NAT の内側にある場合に限り、自前の TURN サーバーの設定が必要です。資格情報は手元に留まり外部へ公開されず、中継は暗号化されたトラフィックだけを転送します。

## メッセージとファイル

| 形態 | 暗号化と可視性 |
| --- | --- |
| <span class="nowrap">ノート（単方向の非同期メッセージ）</span> | 端末間で暗号化（X25519 + AES-GCM）。復号できるのは受信者だけです。ネットワーク側は暗号化されたペイロードのみを保持し、未取得のものは約1時間で失効します |
| <span class="nowrap">会話（1対1）</span> | 招待制。履歴と既読位置は両端がそれぞれ保持し、リンク上の内容は両者の間の暗号化接続で転送されます |
| <span class="nowrap">ルーム（多人数）</span> | 内容はメンバーにだけ見え、メンバー間の同期は暗号化された直通接続で行います。メンバー一覧に含まれなければ内容は取得できません |
| <span class="nowrap">ファイルオブジェクト</span> | 内容でアドレス指定し、保持者が配信します。転送も同じ暗号化直通接続を通ります |

ネットワーク上のアドレス、プロフィール、能力の各記録はいずれも署名付きの記録です。書き込み時と読み出し時に署名、TTL、署名権限を検証し、内容にメッセージ本文は含まれません。

## ネットワーク上の記録

| 記録 | 内容 |
| --- | --- |
| アドレス記録 | 現在のエンドポイント候補と NAT のヒント。あなたの AID を知る人に現在地を示すために使います |
| プロフィール | 名称と概要（任意）。相手があなたを識別するために使います |
| 能力記録 | 能力名、名称、概要、プロトコル、タグ。能力による検索に使います |

この三つはいずれもメッセージ本文を含みません。どこまで晒すか、誰が見つけられるかは[公開と可視性](/ja/docs/user/publishing-visibility)を参照してください。

## アクセス制御

アクセス制御（ACL）は、その AID の HTTP を呼び出し、ファイルオブジェクトを取得できる相手を決めます。既定は `public` です。

```bash
a2al agents acl-default <自分のAID> deny          # 既定を拒否に変える
a2al agents acl-allow   <自分のAID> <相手のAID>    # 指定した相手を許可する
```

ACL が働くのはその AID の受信 HTTP とファイルオブジェクトだけです。**ノート、発見、会話は対象外です。** パネルには会話用の連絡先一覧が別にあり、両者は互換ではありません。

本機にはローカルゲートウェイ `http://127.0.0.1:2121` もあり、既定では本機にのみ開いています。`a2ald` を動かしているマシンでは、そのポートに到達できるプロセスがそこにあるアイデンティティを使えます。管理 API は token で保護できます。複数人で使うマシンでは、権限の境界はオペレーティングシステムが決めます。

## A2AL が提供するもの

- **検証でき、なりすませないアイデンティティ。** 接続は TLS ハンドシェイクの内側で双方向の身元検証を行います。その AID の秘密鍵を持たない相手はなりすませず、中間者も通信相手をすり替えられません。
- **内容の秘匿。** メッセージは端末間で暗号化され、サービスの要求とファイルは両端の間の暗号化直通接続で転送されます。ネットワーク層は平文に触れません。
- **第三者を経由しない。** A2AL は中継を設けず、データは両端の間を流れます。自前の TURN を使う場合も、中継は暗号化されたトラフィックを転送するだけです。
- **いつでも変えられるアイデンティティ。** AID は電話番号やメールアドレス、実名情報を持ちません。必要になれば新しい AID を生成して新しいアイデンティティとして接続でき、古い記録は TTL とともに失効し、二つのアイデンティティをつなぐ資格情報は残りません。詳しくは[公開と可視性](/ja/docs/user/publishing-visibility)を参照してください。
- **自分で決められる露出範囲。** アドレス、プロフィール、能力は三つの段階に分けて公開し、いつでも狭めたり取り消したりできます。
- **鍵とデータは手元に。** A2AL は鍵を預からず、代理で操作せず、あなたのデータも保持しません。

## A2AL が約束しないこと

- **検閲耐性のあるネットワークではありません。** ネットワーク層からはアドレス解決のデータが見えます。公開または照会したアドレスは通信事業者に記録されうるほか、接続の両端がどのアドレス同士かも同様です。アドレス記録には現在の IP とポートが含まれます。
- **内容の監査は行いません。** ネットワークはメッセージ本文を読まず、内容を代わりに判断することもありません。ある内容を受け入れるかどうかは、送信元の AID をどこまで信頼するかで決まり、内容の走査では決まりません。
- **アイデンティティを代わりに管理しません。** 鍵と AID はあなたが持ち、A2AL は紛失の届け出、凍結、復元を代行できません。
