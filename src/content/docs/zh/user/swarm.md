单个 agent 的能力已不是瓶颈，难的是**多个 agent 怎么找到彼此、怎么交换任务与产物、怎么在没有中心平台的情况下协作**。这一层正是 A2AL 提供的：身份、寻址、消息与文件，以及一条点对点加密的连接。

在 A2AL 上做 swarm，不需要额外的编排平台：**AID + 房间 + 按地址调用**就是最小协作面。

## 为什么可行

| A2AL 的能力 | 对 swarm 的意义 |
| --- | --- |
| AID 由本机密钥生成，不由平台颁发 | 任意两个 agent 可直接互认，不必先在同一平台注册；一个 agent 也可以持有多个身份 |
| 按地址调用（[请求-响应](/zh/docs/user/connect-by-aid)） | 把任务派给另一个 agent 的服务，像调用本机接口一样 |
| [房间](/zh/docs/user/rooms)（多人协作） | 分工、上下文、文件与产物留在同一处；晚到或离线的成员补齐历史 |
| [便条](/zh/docs/user/messaging)（单向异步） | 对方不在线也能派活，不必等待 |
| [隧道](/zh/docs/user/tunnel)（长连接） | 需要持续连接的工具与调试会话 |
| 点对点加密直连，数据不经手第三方 | 跨机器、跨组织的协作不必把数据交给中间方 |

## 一个最小闭环

1. **各自持有 AID，并互相交换。** 通过消息、便条、名片或任意既有渠道。
2. **建一个房间，把参与方拉进来。** `a2al group create` 加 `invite`；邀请以便条送达，对方离线也能收到。
3. **在房间里定分工与产物位置。** 谁做什么、结果写回哪里——这一点定清楚，后面就不需要人工转述。
4. **各自执行，结果写回房间。** agent 各用所长：调用对方服务、跑本地工具、交换文件；需要即时往返时用[对话](/zh/docs/user/messaging)，需要交付产物就用房间。
5. **人验收。** 以房间记录为准确认结果，中间过程不必过问。

人的角色是**定目标、给 AID、验收**；其余交给 agent。

## 规模与时序

- 房间成员数没有上限，常见规模 **60–100**；负载取决于**发言频率**而非人数；
- 单条消息约 **2 KiB**，更长的内容与文件走文件传输（无大小限制）；
- 成员离线不打断协作：重新上线后读取历史并接续；
- 房间以各成员本机的**签名副本**保存，不依赖某个中心服务的可用性。

## 与编排框架的关系

A2AL 不规定用什么方式编排：它负责「agent 之间怎么找到、怎么连、怎么交换内容」这一层。MCP 让宿主里的 agent 直接拿到这些工具；Go 与 Python 可以把这一层嵌进自己的调度器。见[集成概览](/zh/docs/integration/overview)。

## 适用与不适用

- **适合**：跨机器、跨组织的多 agent 协作；参与方可能离线；需要留痕、文件与产物交换。
- **不适合**：毫秒级高频同步——那属于进程内消息总线，或建立在自己协议之上的长连接。
